# Server Auth SQLite 自动备份设计

日期：2026-07-26

## 目标

为生产环境 `/root/server-auth/auth.db` 建立独立于 PM2 应用进程的自动灾备能力：

- 每天北京时间 03:15 创建 SQLite 一致性备份；
- 在 VPS 本地使用 AES-256-GCM 加密后上传专用私有 OSS Bucket；
- 使用 ECS RAM 实例角色和最小权限，不保存长期 AccessKey；
- 每日备份保留 14 天；
- 失败时通过钉钉加签机器人立即告警；
- 每月自动下载、解密并验证最新备份可恢复；
- 不停止 `slg-auth`，不影响激活码验证和远程控制服务。

## 非目标

- 不自动覆盖或回滚生产数据库；
- 不把数据库备份放入公开更新 Bucket `slg-updates`；
- 不在应用进程内使用 `setInterval` 调度；
- 不依赖当前未版本化的 PM2 进程配置；
- 不使用运行中数据库文件的普通文件复制作为备份；
- 不在本次范围内实现长期月度归档。

## 当前约束

- `server-auth` 使用 `better-sqlite3`，并启用了 WAL；生产数据库为 `/root/server-auth/auth.db`。
- 数据库包含激活码、设备绑定、心跳、邀请关系、远程验证码和远程会话等敏感信息。
- PM2 管理生产服务，但仓库中没有可完整重建的 ecosystem 配置。
- 当前只有基于 SQLite `.backup` 和 SCP 的人工备份流程。
- 现有 `slg-updates` OSS Bucket 用于公开更新分发，不适合保存数据库备份。

## 架构

采用 systemd timer 调度独立 Node.js 工具，不让备份生命周期依赖 PM2 或 Koa 进程。

计划组件：

```text
server-auth/backup/
├── backup.mjs             # 每日备份入口
├── verify-restore.mjs     # 每月恢复验证入口
├── config.mjs             # 配置读取与校验
├── sqlite.mjs             # 在线快照、完整性和关键表检查
├── crypto.mjs             # AES-256-GCM 加解密
├── oss.mjs                # RAM 角色认证、上传、下载和对象校验
└── dingtalk.mjs           # 钉钉加签和通知

deploy/systemd/
├── slg-auth-backup.service
├── slg-auth-backup.timer
├── slg-auth-verify.service
└── slg-auth-verify.timer
```

各模块保持单一职责；入口文件只编排流程。SQLite、加密、OSS 和钉钉逻辑可以独立测试。

## 配置与机密

生产配置位于：

```text
/etc/slg-auth-backup.env
```

该文件归 `root:root` 所有，权限为 `0600`，至少包含：

```text
BACKUP_DB_PATH=/root/server-auth/auth.db
BACKUP_OSS_REGION=oss-cn-shanghai
BACKUP_OSS_BUCKET=slg-auth-backups-<阿里云账号唯一后缀>
BACKUP_OSS_PREFIX=daily/
BACKUP_ENCRYPTION_KEY=<Base64 编码的随机 32 字节密钥>
DINGTALK_WEBHOOK=<加签机器人 Webhook>
DINGTALK_SECRET=<SEC... 加签密钥>
```

加密密钥必须另外保存到用户的密码管理器或离线介质。密钥不进入 Git、OSS、数据库、钉钉消息或 systemd unit。丢失全部密钥副本将导致备份不可恢复。

OSS 临时凭证通过 ECS RAM 实例角色运行时获取，不保存长期 AccessKey。

## 调度

- 每日备份：北京时间每天 03:15；
- 每月验证：北京时间每月 1 日 04:15；
- timer 明确使用 `Asia/Shanghai` 语义；
- `Persistent=true`：VPS 在计划时间因外部原因关机或不可用时，下次启动后补执行一次错过的任务；该配置不会主动关机或重启 VPS；
- 使用随机秒级延迟，避免任务严格集中在固定秒；
- 每日备份与每月验证共享互斥锁，禁止重叠；
- service 设置最大执行时间为 15 分钟。

## 每日备份流程

阶段名称固定为：

```text
preflight → snapshot → integrity → encrypt → upload → verify-upload → cleanup
```

### 1. 启动前检查

- 数据库路径必须是绝对路径；
- 数据库必须存在、是普通文件且不是符号链接；
- 验证 Bucket、Region、对象前缀、加密密钥和钉钉配置；
- 获取互斥锁；无法获取时以失败退出并告警。

### 2. SQLite 一致性快照

通过 SQLite 在线 Backup API 创建唯一临时快照。禁止直接复制运行中的 `auth.db`，因为 WAL 中可能存在尚未合并到主文件的已提交数据。

备份不停止 PM2，不修改生产数据库，不中断正常请求。

### 3. 快照校验

- 快照大小必须大于零；
- 执行 `PRAGMA integrity_check`，唯一成功结果必须为 `ok`；
- 验证业务关键表存在，并执行最小只读查询；
- 校验失败时不加密、不上传。

关键表列表应由实现阶段根据 `AuthDatabase.ts` 的生产 schema 固定定义，至少覆盖激活码、设备绑定和远程会话的核心表。

### 4. AES-256-GCM 加密

- 使用随机生成的 32 字节主密钥；
- 每份备份生成新的随机 nonce；
- 自描述密文格式包含魔数、格式版本、nonce、认证标签和密文；
- 使用明确的附加认证数据绑定格式版本；
- 计算完整加密对象的 SHA-256；
- 密文任何篡改都必须导致认证失败；
- systemd 设置 `UMask=0077`，临时明文和密文默认仅 root 可读写。

### 5. OSS 上传与确认

对象键采用可排序且唯一的时间格式，例如：

```text
daily/2026/07/auth-20260726T031500+0800.db.enc
```

对象元数据包含：

- 加密格式版本；
- 加密对象 SHA-256；
- 原始快照大小；
- 创建时间；
- 非敏感运行标识。

上传后执行 HEAD，核对对象大小和元数据。只有核对成功才将本次任务标记为成功。

### 6. 清理

无论成功或失败，均在 `finally` 路径关闭数据库句柄并清理本次唯一临时目录中的明文和密文。生产数据库不参与清理。

## OSS 与 RAM 权限

创建专用私有 Bucket，与 `slg-updates` 完全隔离。建议与 ECS 同地域，使用标准存储，不开启公共读或静态网站托管。

创建并绑定专用 ECS RAM 角色，例如 `SlgAuthBackupRole`。角色仅允许指定 Bucket 的 `daily/` 前缀执行：

- 上传对象；
- 查询对象元数据；
- 列出对象；
- 下载对象。

不授予：

- 删除对象；
- 修改 Bucket ACL；
- 修改生命周期；
- 访问其他 Bucket；
- `AliyunOSSFullAccess`。

优先使用加固模式的 ECS 实例元数据访问方式获取临时凭证，临时凭证只存在于进程内存。

## 保留策略

由 OSS Bucket 生命周期规则自动删除超过 14 天的 `daily/` 对象。备份程序本身不拥有删除权限，也不执行批量清理，以降低错误删除全部历史备份的风险。

生命周期规则属于 Bucket 管理配置，不授予 ECS RAM 角色修改权限。上线验收时必须人工核对规则前缀和 14 天期限。

## 钉钉通知

使用钉钉群自定义机器人的 Webhook 与 `SEC...` 加签密钥。脚本按钉钉协议使用时间戳和 HMAC-SHA256 生成签名。

通知策略：

- 每日备份成功：仅写 systemd journal，不发送消息；
- 任一每日备份阶段失败：立即发送告警；
- 每月恢复验证成功：发送一条成功证明；
- 每月恢复验证失败：立即发送告警。

告警只包含环境、实例标识、阶段、时间、运行标识和脱敏错误摘要。禁止包含 AES 密钥、完整 Webhook、钉钉 Secret、OSS 临时凭证、激活码、设备指纹或数据库内容。

钉钉发送失败不能覆盖原始错误：原始错误始终写入 journal，通知失败作为附加错误记录，任务仍以非零状态退出。

## 每月恢复验证

每月任务执行非破坏性验证：

1. 通过 RAM 角色列出 `daily/` 对象；
2. 根据对象键与元数据选择最新备份；
3. 下载到唯一临时目录；
4. 核对对象大小、SHA-256 和加密格式版本；
5. 使用 AES-256-GCM 解密；
6. 执行 `PRAGMA integrity_check`；
7. 验证关键表并执行只读查询；
8. 关闭数据库并清理临时明文和密文；
9. 发送成功证明或失败告警。

该任务不连接、不覆盖、不修改生产数据库，也不修改 OSS 对象。成功通知包含验证时间、被验证备份的创建时间、脱敏对象名、完整性结果和耗时，不包含业务数据。

## 人工灾难恢复

提供运维文档描述真实恢复步骤：

1. 从 OSS 选择并下载指定备份；
2. 校验对象 SHA-256 和加密格式；
3. 使用离线保存的密钥解密；
4. 对恢复文件执行完整性和关键表检查；
5. 停止 `slg-auth`；
6. 保留当前数据库及 WAL/SHM 作为现场副本；
7. 隔离旧 `auth.db-wal` 和 `auth.db-shm`；
8. 通过同文件系统内的原子替换安装恢复后的 `auth.db`；
9. 设置正确属主与权限；
10. 启动服务；
11. 验证 `/health`、管理查询和一次受控激活流程。

自动月度验证不自动执行生产替换，避免误恢复导致业务数据回滚。

## systemd 安全边界

service 采用基础沙箱限制，并只开放完成任务所需的能力：

- `UMask=0077`；
- 只读访问生产数据库及其父目录；
- 只写专用运行时/临时目录；
- 允许访问 ECS 元数据、OSS 和钉钉所需网络；
- 禁止写入应用代码目录；
- 设置执行超时和非零失败状态；
- 使用 `flock` 对 `/run/lock/slg-auth-backup.lock` 加排他锁，备份与验证任务共享该锁。

具体 systemd hardening 选项在实施时以不破坏 SQLite 在线读取、DNS、TLS 和 ECS 元数据访问为前提逐项验证。

## 日志与可观测性

日志使用单行结构化 JSON，写入 stdout/stderr 并由 journald 收集。每条日志包含：

- 运行标识；
- 阶段；
- 开始/结束时间；
- 耗时；
- 文件大小；
- OSS 对象键；
- 成功或失败状态。

查看命令：

```bash
journalctl -u slg-auth-backup.service
journalctl -u slg-auth-verify.service
systemctl list-timers 'slg-auth-*'
```

结构化日志和异常序列化均需经过脱敏，不能输出任何机密或业务数据。

## 错误处理

- 任一阶段失败立即停止后续业务步骤；
- 清理逻辑始终执行；
- 任务以非零状态退出，使 systemd 标记失败；
- 告警包含失败阶段和脱敏摘要；
- OSS 上传确认失败时不得宣称成功；
- 清理失败应记录并告警，但不得覆盖更早的主错误；
- 任务超时由 systemd 终止并记录失败；
- 每次使用唯一临时目录和唯一对象键，避免并发覆盖。

## 测试设计

自动测试至少覆盖：

- 配置缺失、格式错误和相对数据库路径时拒绝运行；
- 非普通文件或符号链接数据库路径时拒绝运行；
- WAL 模式下在线快照包含已提交数据；
- SQLite 完整性检查失败；
- 关键表缺失；
- AES-256-GCM 加解密往返；
- 密文、nonce、认证标签或附加认证数据被篡改时解密失败；
- 多次备份使用不同 nonce；
- 钉钉加签结果符合固定测试向量；
- OSS 上传后对象大小或元数据不一致；
- 月度任务正确选择最新对象；
- 成功和各失败路径均清理临时文件；
- 日志、异常与通知不泄露配置中的敏感值；
- 互斥锁阻止重叠任务。

OSS、ECS 元数据和钉钉通过依赖注入或适配器进行模拟，不让常规单元测试访问真实云资源。

## 首次部署与验收

首次部署按以下顺序完成：

1. 创建专用私有 OSS Bucket；
2. 配置 `daily/` 前缀 14 天生命周期；
3. 创建最小权限 RAM 策略和 ECS 实例角色并绑定实例；
4. 创建钉钉加签机器人；
5. 生成随机 32 字节 AES 密钥并离线保存副本；
6. 安装受限环境文件和 systemd units；
7. 重新加载 systemd 并启用 timers；
8. 手动启动一次每日备份 service；
9. 验证 OSS 私有对象、大小、元数据和生命周期；
10. 确认 VPS 不残留明文快照；
11. 手动启动一次恢复验证 service；
12. 确认手机收到成功通知；
13. 制造一次无害配置失败，确认钉钉告警和非零退出；
14. 确认 `slg-auth` 全程可用；
15. 查看 timer 下一次执行时间。

验收通过后，仍应定期人工抽查最新备份日期和每月验证消息。自动化备份不能替代对恢复流程的人工熟悉。
