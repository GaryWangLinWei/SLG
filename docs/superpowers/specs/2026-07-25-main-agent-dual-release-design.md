# 主版与代理商版双版本发布设计

## 背景

项目当前每次发布只构建一个 Electron Windows 安装包，并通过阿里云 OSS 的 `updates/` 目录提供自动更新。

需要在每次发布时同时产出主版和代理商版。两个版本使用同一份源码、相同业务版本号和相同安装身份，不允许在同一台电脑上并存。代理商版只隐藏两个商业入口：

1. 激活页面的“在线购买”；
2. 顶部栏的“续费”。

代理商版仍保留现有激活码输入界面，用户从代理商处取得激活码。邀请码、激活按钮、授权等级、剩余时间、“同步授权”和“邀请好友”均保持现状。

两个版本必须使用独立更新源，不能互相收到对方的安装包。主版现已完成 OSS 迁移，两个版本都只发布到 OSS，不再更新 VPS 上的历史更新文件。

## 目标

- 一次发布同时构建主版和代理商版；
- 两个版本共享 `package.json.version` 和 release notes；
- 安装包文件名能够区分版本；
- 安装后产品名、窗口标题、快捷方式、安装目录和卸载项保持一致；
- 安装另一个版本时覆盖现有版本，并切换为新安装包对应的界面能力和更新源；
- 主版与代理商版分别从独立 OSS 目录自动更新；
- 任一版本构建或上传失败时，将整次发布判定为失败，并尽可能恢复到两个渠道都未生效新版本的状态。

## 非目标

- 不为代理商版增加独立品牌、图标、窗口标题或安装目录；
- 不允许两个版本并存；
- 不改变现有许可证服务、激活码规则或本地许可证存储；
- 不隐藏邀请好友、授权等级、剩余时间或同步授权；
- 不把 UI 隐藏作为安全边界，本地许可证 API 保持现状；
- 不删除 VPS 上已有的历史更新文件，只停止继续上传；
- 本阶段不支持主版和代理商版使用不同版本号或独立发布时间。

## 1. 构建版本模型

### 1.1 Edition

引入唯一的构建期版本标识 `edition`：

- `main`：主版；
- `agent`：代理商版。

构建入口必须显式提供 edition。缺失或值不在上述集合内时立即失败，不进行默认推断，避免生成渠道不明的安装包。

edition 必须由同一个构建入口同时传递给 Electron/electron-builder 和 Vite 前端。不能分别手工设置两个环境变量，否则可能产出“代理商 UI + 主版更新源”一类混合包。

edition 是构建期常量，不从 localStorage、配置文件或命令行运行参数读取，用户不能在已安装应用内切换版本。

### 1.2 相同安装身份

两个版本保持相同：

- Electron `appId`：`com.rok.automation`；
- `productName`：`ROK助手`；
- Windows AppUserModelId；
- 安装目录、快捷方式和卸载项名称。

因此两个版本不能并存。安装另一版本会覆盖现有版本。新安装包内固化的 edition 和更新地址随覆盖安装一起切换，不保留旧渠道标记。

插件 ID 虽然当前也使用 `com.rok.automation`，但它与 Electron appId 是不同概念。本功能不修改插件 ID，避免破坏前端任务调用和插件注册。

### 1.3 产物命名与输出隔离

两个版本共享同一版本号，例如 `1.2.0`，但安装包名不同：

| Edition | 安装包名 |
|---|---|
| `main` | `ROK助手 Setup 1.2.0.exe` |
| `agent` | `ROK助手-代理商版 Setup 1.2.0.exe` |

对应 blockmap 使用相同文件名追加 `.blockmap`。

两次构建必须使用不同的临时输出目录，避免第二次构建覆盖第一次的安装包、blockmap 或 `latest.yml`。发布工具不能依赖 electron-builder 隐式生成的默认名称，应通过明确配置或 edition 元数据计算和校验预期产物。

## 2. 前端能力差异

建立集中式 edition 能力配置：

```ts
main: {
  showPurchaseEntry: true,
  showRenewEntry: true,
}

agent: {
  showPurchaseEntry: false,
  showRenewEntry: false,
}
```

组件只读取语义化能力，不在各处散落 `edition === 'agent'` 判断。

### 2.1 激活页面

`Activation.tsx` 根据 `showPurchaseEntry` 决定是否渲染“在线购买”。

代理商版仍显示：

- 激活码输入；
- 邀请码输入；
- 激活按钮；
- 到期、设备指纹不匹配和离线状态提示；
- 设备绑定及离线说明。

用户从代理商处获取激活码，现有 `/api/license/activate` 和 `/api/license/preview` 流程不变。

### 2.2 顶部栏

`App.tsx` 根据 `showRenewEntry` 决定是否渲染顶部“续费”按钮及其弹窗入口。

代理商版仍显示：

- 授权等级；
- 剩余时间；
- 同步授权；
- 邀请好友。

### 2.3 诊断信息

Electron 主进程在应用启动和检查更新时记录当前 edition 与更新目录，便于排查构建错配或更新串线。正常界面不额外显示“代理商版”。日志不得包含激活码等敏感信息。

## 3. 独立自动更新

### 3.1 OSS 文件布局

```text
updates/
├─ latest.yml
├─ ROK助手 Setup 1.2.0.exe
├─ ROK助手 Setup 1.2.0.exe.blockmap
└─ agent/
   ├─ latest.yml
   ├─ ROK助手-代理商版 Setup 1.2.0.exe
   └─ ROK助手-代理商版 Setup 1.2.0.exe.blockmap
```

更新源：

| Edition | OSS 更新目录 |
|---|---|
| `main` | `/updates` |
| `agent` | `/updates/agent` |

主版保留现有 `/updates`，已安装的主版客户端无需迁移。代理商版从首次发布起固定使用 `/updates/agent`。

两个版本使用各自构建包内固化的 generic provider URL。覆盖安装另一个版本后，后续自动更新自然切换到新安装版本的更新目录。

### 3.2 仅使用 OSS

双版本发布流程只上传 OSS：

- 不上传 VPS；
- 不保留发布命令中的 VPS fallback；
- 不需要 `--oss-only` 来区分发布目标；
- 不删除 VPS 上已有历史文件，但后续不再更新它们。

## 4. 发布事务

一次发布包含三个阶段。

### 4.1 构建与本地验证

1. 使用同一个 `package.json.version` 分别构建 `main` 和 `agent`；
2. 验证两个 `latest.yml` 的版本都等于 `package.json.version`；
3. 验证各自 manifest 引用正确渠道的安装包；
4. 验证安装包和 blockmap 均存在；
5. 验证两个版本使用预期更新目录；
6. 任一检查失败时立即退出，不上传任何文件。

### 4.2 上传不可变产物

先上传两版安装包和 blockmap，再验证四个远端对象均存在且可读取。

在这一阶段，线上 `latest.yml` 尚未更新，客户端继续看到旧版本。中途失败只会留下未被 manifest 引用的新产物，不会触发不完整更新。

不自动删除这些未生效产物：保留它们便于安全重试，也避免远端删除操作。

### 4.3 发布 manifest

只有两版不可变产物全部上传并验证成功后，才发布两份 `latest.yml`。

发布前读取并保存两个线上旧 manifest。发布顺序可以固定，但脚本必须记录哪些 manifest 已成功替换。

OSS 不支持两个对象之间的跨对象事务，因此无法保证严格原子提交。如果第一份新 manifest 上传成功而第二份失败：

1. 停止发布；
2. 恢复本次已经更新渠道的旧 manifest；
3. 验证恢复后的远端内容；
4. 以非零状态退出；
5. 明确报告原始失败和回滚结果。

如果回滚本身失败，不能声称整体发布已恢复；脚本必须以显著错误报告受影响的渠道和当前不确定状态，等待人工处理。

“整体失败”的操作语义是：任何阶段失败都不会被报告为成功，并在 manifest 阶段尽最大努力恢复已切换的渠道。由于 OSS 缺少跨对象事务，短暂的不一致窗口和回滚失败风险无法完全消除。

## 5. 错误处理

以下情况必须以非零状态退出：

- edition 缺失或非法；
- 任一 edition 构建失败；
- 两版版本号不一致；
- 安装包、blockmap 或 manifest 缺失；
- manifest 引用另一渠道的文件；
- 构建包内更新地址与 edition 不匹配；
- 任一不可变产物上传或远端验证失败；
- 任一 manifest 上传失败；
- manifest 回滚或回滚验证失败。

错误输出应包含：

- 当前阶段；
- edition；
- 文件或 OSS 对象路径；
- 原始错误；
- 是否开始回滚；
- 每个渠道的回滚结果。

不得输出 OSS 密钥、许可证令牌或激活码。

## 6. 测试策略

### 6.1 单元测试

覆盖：

- edition 只接受 `main | agent`；
- 主版能力显示购买和续费；
- 代理商版能力隐藏购买和续费；
- edition 映射到正确安装包名和更新地址；
- 发布校验拒绝缺文件、版本不一致、错误文件名和跨渠道 manifest；
- 上传顺序固定为“两版不可变产物 → 两版 manifest”；
- 第二份 manifest 失败后恢复第一份；
- 回滚失败会被明确报告并使发布失败。

### 6.2 前端组件测试

验证主版：

- 激活页显示“在线购买”；
- 顶部显示“续费”。

验证代理商版：

- 激活页不显示“在线购买”；
- 顶部不显示“续费”；
- 激活码输入、激活按钮、剩余时间、同步授权和邀请好友仍可见。

### 6.3 构建验证

对两个构建目录检查：

- 版本号一致；
- 安装包文件名符合 edition；
- `latest.yml` 引用本目录安装包；
- blockmap 存在；
- 应用内置更新地址正确；
- 代理商版前端产物不包含可达的购买或续费入口。

## 7. 发布后人工验收

每次首次启用或发布流程变更后验证：

1. OSS 两个 `latest.yml` 版本相同；
2. 两份 manifest 分别引用本渠道安装包；
3. 主版旧客户端只能收到主版更新；
4. 代理商版只能收到代理商版更新；
5. 两个安装包可以相互覆盖安装；
6. 覆盖后产品名、快捷方式和安装目录保持不变；
7. 覆盖后界面入口符合新安装包 edition；
8. 覆盖后后续更新来自新安装包对应渠道；
9. 应用账号配置和许可证在覆盖安装后保持不变；
10. 代理商版仍能使用代理商提供的激活码完成激活。

## 8. 风险与约束

### 8.1 相同 appId 的渠道切换

两个版本刻意使用相同安装身份。覆盖安装时 updater 配置是否可靠替换必须通过真实 Windows 安装包验证，不能只依赖单元测试推断。

### 8.2 发布不具备严格跨对象原子性

两个 OSS manifest 无法事务性同时切换。通过“产物先行、manifest 最后、失败回滚”降低风险，但仍存在短暂不一致和回滚失败的可能。发布脚本必须如实报告状态。

### 8.3 UI 隐藏不是安全边界

代理商版仍包含许可证 API 和激活能力。此次需求是渠道体验差异，不防止具备本地调试能力的用户调用接口或检查前端资源。

### 8.4 许可证与数据共享

两版使用相同应用身份，并保持现有 `~/.slg-automation` 数据路径。覆盖安装后账号配置和许可证应继续可用，这是预期行为，不对数据做 edition 隔离。

## 9. 成功标准

本功能完成需同时满足：

- 一条发布命令能从同一源码和版本号构建两个安装包；
- 两个安装包仅文件名不同，安装后产品身份一致且不能并存；
- 代理商版仅隐藏“在线购买”和顶部“续费”；
- 两个版本分别通过 `/updates` 与 `/updates/agent` 更新，不会串线；
- 两版构建或上传任一失败时，发布命令失败且不会被报告为成功；
- 发布只使用 OSS，不再更新 VPS；
- 覆盖安装、许可证保留和渠道切换经过真实安装包人工验证。
